# Speedify Browser & Torrent

A small Docker-based desktop setup that runs Firefox and qBittorrent
through Speedify without routing the rest of the host through the VPN.
The project began as an experiment to run Speedify VPN on CachyOS, even
though it is not supported for ARCH systems.

qBittorrent was added later and now shares the same VPN session. Both
applications start together; either can be closed independently, and
Speedify remains active until both have exited.

The setup was developed on CachyOS with XFCE and X11. It is
intentionally pragmatic rather than a general-purpose or hardened
desktop-container solution.

## What it does

Launching **VPN Browser & Torrent**:

1.  Checks whether Docker is already running and starts it if necessary.
2.  Starts the container and Speedify daemon.
3.  Opens the Speedify GUI.
4.  Connects Speedify and waits until the VPN has remained connected for
    10 seconds.
5.  Starts qBittorrent and Firefox.
6.  Keeps Speedify running while either application is still running.
7.  Shuts down Speedify and the container when both applications have
    exited.
8.  Stops Docker only if this launcher originally started it.

Closing the Speedify GUI does not disconnect the VPN or stop the
container. Normal host applications continue to use the host network.

## Requirements

The host needs:

-   Linux with X11
-   Docker with Docker Compose
-   systemd
-   `xhost`
-   `/dev/net/tun`
-   a Speedify account/subscription

The launcher assumes the required `systemctl` commands can be run with
**passwordless `sudo`**. This is deliberate: the application-menu
shortcut uses `Terminal=false`, so there is no terminal available for a
sudo password prompt.

If that does not suit your system, adapt the privilege model rather than
expecting the current desktop shortcut to prompt for a password.

## Installation

Clone and build:

``` bash
git clone https://github.com/Scandal-UK/speedify-browser.git
cd speedify-browser
docker compose build
```

Install the application-menu shortcut:

``` bash
chmod +x install.sh
./install.sh
```

The installer creates **VPN Browser & Torrent** under the user's
application menu. It resolves the repository location and writes an
absolute `Exec=` path because desktop entries do not expand `$HOME`.

The host launcher remains named `vpn-browser` for historical reasons.

## First run

Launch **VPN Browser & Torrent** and log into Speedify using its GUI.
The authentication state is then persisted on the host.

Firefox and qBittorrent configuration are also persisted.

### Required qBittorrent configuration

One important setting is deliberately not modified automatically.

On the first qBittorrent launch after a clean installation:

1.  Open **Tools → Options → Advanced**.
2.  Set **Network interface** to `connectify0`.
3.  Apply the setting.

`connectify0` is Speedify's tunnel interface inside the container. Do
not leave qBittorrent set to `Any interface`: binding it to
`connectify0` prevents its BitTorrent listener from falling back to
Docker's ordinary `eth0` interface when the VPN disappears.

Also disable **Close qBittorrent to notification area** if closing its
window should count as exiting qBittorrent. Otherwise the window
disappears but the process remains alive, correctly keeping the VPN
session running.

UPnP/NAT-PMP can also be disabled. During testing, qBittorrent's
attempts to map the Speedify-side address failed because no suitable
router was available.

Verify the persisted interface setting with:

``` bash
docker exec speedify-browser \
    grep -E 'Session\\Interface' \
    /root/.config/qBittorrent/qBittorrent.conf
```

Expected:

``` ini
Session\Interface=connectify0
Session\InterfaceName=connectify0
```

## qBittorrent VPN-loss behaviour

The binding was tested with qBittorrent 4.5.2 by deliberately
disconnecting Speedify.

When Speedify removed `connectify0`, qBittorrent detected the change and
logged:

``` text
Network configuration of connectify0 has changed, refreshing session binding
The configured network interface is invalid. Interface: "connectify0"
Trying to listen on the following list of IP addresses: "connectify0:64846"
```

It did not rebind its BitTorrent listener to Docker's `eth0`.

When Speedify reconnected and recreated `connectify0`, qBittorrent
detected the interface returning and automatically refreshed its
binding.

The listening port is generated by qBittorrent and will vary.

## Persistent data

Runtime data lives below `data/`, which is excluded from Git:

``` text
data/
├── firefox/
├── qbittorrent/
│   ├── config/
│   └── share/
└── speedify/
    ├── keys/
    └── logs/
```

The public repository therefore contains no Speedify authentication
state, browser profile or qBittorrent state.

The host's `~/Downloads` is mounted as `/root/Downloads` and is
available to both Firefox and qBittorrent.

### Firefox

`data/firefox/` persists bookmarks, extensions and settings. Firefox ESR
comes from Debian; rebuilding the image is the intended update
mechanism.

### qBittorrent

`data/qbittorrent/config/` and `data/qbittorrent/share/` persist
qBittorrent configuration and state, including the `connectify0`
preference once it has been set.

Because `data/` is ignored, a completely fresh clone requires the
first-run configuration above.

### Speedify authentication

Persisting Speedify's `logs` alone is not sufficient. Speedify starts
its daemon using a `.keys` directory:

``` bash
./speedify -d logs -k .keys &
```

The directory contains encryption material used for settings and
authentication tokens, including files such as `rsa_key.seed` and
`rsa_key.der`.

Both of these must therefore persist together:

``` text
/usr/share/speedify/logs
/usr/share/speedify/.keys
```

An old `logs` directory without its matching keys should not be
considered a usable authenticated backup.

If preserving a working installation across an OS rebuild matters, back
up the complete `data/` directory securely. Do not commit it.

## Networking

The container gets TUN access and network-administration capability:

``` yaml
devices:
  - /dev/net/tun:/dev/net/tun

cap_add:
  - NET_ADMIN
```

`privileged: true` is not required.

### Reverse-path filtering

A major part of getting Speedify stable in Docker was reverse-path
filtering.

Speedify's own startup scripts attempt to disable it, but `/proc/sys` is
read-only from inside the container. Docker therefore applies:

``` yaml
sysctls:
  net.ipv4.conf.all.rp_filter: "0"
  net.ipv4.conf.default.rp_filter: "0"
```

Before this change Speedify could briefly report `CONNECTED` and then
return to `CONNECTING`, with the tunnel failing to receive traffic.

Do not remove these settings merely because Speedify's own startup
script may still print warnings while trying to modify `/proc/sys`.

## X11 and GUI applications

The host X socket is mounted into the container and `DISPLAY` is passed
through.

The host launcher grants the container's root user access with:

``` bash
xhost +SI:localuser:root >/dev/null
```

This is a pragmatic solution for this personal desktop setup, not a
hardened X11 isolation model.

Firefox and qBittorrent currently run as root inside the container, so
files created in host-mounted directories may be root-owned. Running the
applications under a UID/GID matching the host is a possible future
improvement.

### Speedify UI

The supported GUI wrapper is:

``` text
/usr/share/speedifyui/speedify_ui
```

The working container also uses:

``` yaml
security_opt:
  - seccomp=unconfined

stdin_open: true
tty: true
```

The pseudo-TTY is important. During development the Speedify UI
processes could be running while no window appeared. Allocating a TTY
and launching the wrapper normally made automatic GUI startup reliable.

Warnings concerning `/dev/dri`, Radeon/DRI, ALSA or software rendering
have occurred while the GUI was working normally. The GPU is
deliberately not exposed merely to remove those warnings. qBittorrent
can produce similar harmless graphics warnings.

## Application lifecycle

Speedify is shared by Firefox and qBittorrent.

After the VPN has remained connected for 10 seconds, both applications
are started as child processes. The entrypoint remains alive while
either application is running:

``` text
Firefox open    + qBittorrent open    -> VPN stays up
Firefox closed  + qBittorrent open    -> VPN stays up
Firefox open    + qBittorrent closed  -> VPN stays up
Firefox closed  + qBittorrent closed  -> VPN shuts down
```

If qBittorrent appears closed but Speedify remains active, check the
notification area. qBittorrent can hide there instead of terminating if
its close-to-tray preference is enabled.

The entrypoint cleanup trap shuts down the Speedify UI and daemon when
both protected applications have genuinely exited.

## Docker lifecycle

Docker is intentionally not required to run continuously.

The host launcher checks whether `docker.service` is active. If not, it
starts Docker and remembers that it did so. When the container exits, it
runs `docker compose down`.

If this launcher originally started Docker, it stops both:

``` bash
sudo systemctl stop docker.service docker.socket
```

Stopping both matters because leaving `docker.socket` active can
socket-activate Docker again.

If Docker was already running before launch, it is left running. Both
cases have been tested.

## Rebuilding after an OS reinstall

For a clean machine:

1.  Install Docker/Compose and `xhost`.
2.  Configure passwordless `sudo` as expected by the launcher, or adapt
    the launcher to your preferred privilege model.
3.  Clone this repository.
4.  Run `docker compose build`.
5.  Run `./install.sh`.
6.  Launch **VPN Browser & Torrent**.
7.  Log into Speedify.
8.  Set qBittorrent's **Tools → Options → Advanced → Network interface**
    to `connectify0`.
9.  Disable **Close qBittorrent to notification area** if closing its
    window should terminate it.
10. Verify the interface setting using the command above.

If a secure backup of `data/` is restored instead, Firefox, qBittorrent
and Speedify state can be retained. Speedify's `logs` and `.keys` must
be restored as a matching pair.

## Useful diagnostics

Speedify state:

``` bash
docker exec speedify-browser \
    /usr/share/speedify/speedify_cli state
```

VPN interface:

``` bash
docker exec speedify-browser \
    ip addr show connectify0
```

qBittorrent interface setting:

``` bash
docker exec speedify-browser \
    grep -E 'Session\\Interface' \
    /root/.config/qBittorrent/qBittorrent.conf
```

qBittorrent sockets:

``` bash
docker exec speedify-browser \
    sh -c 'ss -tunap | grep qbittorrent'
```

Container processes:

``` bash
docker exec speedify-browser \
    ps -eo pid,ppid,state,comm,args
```

## Intentional design choices

Several details may look unusual but are based on behaviour observed
during development:

-   Docker is started on demand rather than enabled permanently.
-   Passwordless `sudo` is assumed.
-   `rp_filter` is disabled inside the container namespace.
-   `seccomp=unconfined` is currently used for the Speedify WebKit UI.
-   A pseudo-TTY is allocated because it was required for reliable UI
    startup.
-   The container root user is granted X11 access with `xhost`.
-   Firefox and qBittorrent currently run as root.
-   qBittorrent must be manually bound to `connectify0` after a clean
    installation.
-   Closing the Speedify GUI does not own the VPN lifecycle.
-   The container remains alive until both Firefox and qBittorrent have
    exited.

## Scope

This is a personal Linux desktop utility, not a general-purpose VPN
gateway.

Its intended scope is deliberately narrow:

``` text
Speedify
├── Firefox
└── qBittorrent
```

Other host applications are not routed through the VPN.

Possible future improvements include running applications under a
non-root UID/GID, automatically validating or provisioning qBittorrent's
`connectify0` binding, and adding lightweight prerequisite checks to
`install.sh`.
